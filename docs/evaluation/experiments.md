# Experiments

## Energy forecasting experiment

This is the repository's current reproducible quantitative model experiment.

### Prerequisites

- Python environment installed with project dependencies.
- An inspected Berlin-scoped Stromnetz Berlin grid-load publication or local copy.
- Exact timestamp/value column names.
- Correct unit and source timezone.
- Provenance URL when the input is a local copy.

The repository does not bundle the provider dataset as an embedded benchmark fixture.

### Execute

```bash
python scripts/evaluate_energy.py \
  --input <local-csv-or-verified-stromnetz-url> \
  --source-url <required-for-local-copy> \
  --dataset "<exact inspected dataset title>" \
  --timestamp-column "<exact timestamp column>" \
  --value-column "<exact value column>" \
  --unit MW \
  --source-timezone Europe/Berlin \
  --seasonal-lag 96 \
  --test-fraction 0.2 \
  --state data/runtime/energy.json
```

Omit `--source-url` only when `--input` itself is the verified `https://www.stromnetz.berlin/...` URL.

### Output

The command prints:

- energy-state path;
- selected model;
- MAE and RMSE;
- persistence baseline ID and baseline MAE;
- forecast validity timestamp;
- forecast point value/unit; and
- dataset fingerprint.

It persists the selected evaluation and one forecast artefact to the configured energy state file.

### Reproduction record

For a publishable/repeatable run record at least:

- repository commit SHA;
- Python/package environment (ideally lock/container digest or `pip freeze` snapshot);
- exact source URL/file checksum and provider publication title/date;
- CLI arguments;
- dataset fingerprint emitted by the workflow;
- generated evaluation/forecast JSON;
- hardware only if runtime/performance is being compared.

### Interpretation

The selected model is the best candidate on the single chronological holdout under the current MAE-first selection rule. The experiment is not nested cross-validation, not probabilistic forecasting and not evidence that the same model will remain best after distribution shift.

## Live provider compatibility experiment

Run:

```bash
python scripts/live_smoke.py
```

or execute the `Live source smoke` GitHub Actions workflow.

Purpose: verify that current public live-provider interfaces remain compatible with adapters and produce acceptable source status.

This is an operational compatibility check. Provider counts/freshness at one timestamp are not a longitudinal reliability evaluation.

## Reference-source compatibility experiment

The `Reference source smoke once` workflow invokes `ReferenceAcquisitionCoordinator().refresh(include_gtfs=True)` and asserts that official facilities, climate features and VBB static stops are non-empty with no reference errors.

OSM is not part of that check.

## Deterministic scenario experiments

Scenario and resilience tests exercise known synthetic network/observation fixtures to verify transformations and invariants. They are algorithm tests, not empirical Berlin scenario validation.

A future scientific scenario experiment should define a historical event or external benchmark, source snapshots, hypotheses, outcome variables and baseline methods before result claims are added.

## Experiment artefact policy

Do not commit invented or manually edited metric tables as research results. Result artefacts should be generated by a documented command from identified input data and repository version.
